01

Finance Platform

One system runs the building's money, from booking a room to closing the books. Every bill, payment and deposit lands in a double-entry ledger, and the bank statement is the only way a bill gets paid.

What it does

ModuleWhat it handles
BookingsShort-term stays: create, extend, cancel, check-out with a meter reading
LeasesLong-term tenancies that bill monthly
ReadingsElectricity and water meters, photographed at check-in and check-out
BillsInvoices, the monthly billing run, PDF invoices, guest accounts across stays
ReconBank statement import and line-by-line reconciliation to bills, deposits or accounts
ReportsBalance sheet, P&L, receivables, general ledger, trial balance, rent roll, occupancy

How it is architected

Bills and bank lines are the only two roads into the ledger, and both go through the same module.

Web app and API in one

Next.js App Router: 115 screens and 191 API routes. Users sign in, and role-based permissions decide what each of six roles can see and do.

Postgres as the source of truth

148 hand-written SQL migrations. Rules that must never break live in the database as constraints and triggers, so they hold for scripts and imports too.

Deposits are a liability

A bill debits Receivables and credits income; a deposit is credited to a liability account and never counted as income until it is settled at check-out.

Hosted and monitored

Runs as a cloud web app on a managed Postgres database, with error monitoring and automatic checks in the release process.

Controls it enforces

ControlHow
Every entry balancesThe posting module refuses any entry whose debits and credits differ, and rolls the transaction back
Payments only from the bankA bill cannot be marked paid by hand. It is paid only by allocating a bank line, or from a deposit held
Closed months stay closedA reconciled month can be locked; matches, deletes and re-imports inside it are refused
Deletes leave no orphansDeleting a bill deletes its ledger entries in the same transaction; a foreign key refuses it otherwise
Every ledger line names its customerEach line carries its bill, tenant and unit, so receivables split by customer and tie to each statement
Unknown money is parkedUnidentified receipts go to a suspense account that the dashboard asks someone to clear
Transfers are flaggedA statement line naming one of the company's own accounts is flagged as an internal transfer
Data stays consistentTriggers stop a meter reading outside its tenancy, or a short-term booking on a long-term unit
Who did whatAn audit log records each change with before and after values

02

Cleaning Operations App

One web app plans each day's cleaning round, takes attendance from the door system, and shows the live board on two TVs in the staff room. It replaced a paper rota and a group chat.

Scheduling logic

Fixed weekdays first

A room set to named days beats a frequency rule. Fixed days replaced "due N days after the last clean", which drifted round the week.

Two every-other-day patterns

A is Sat/Mon/Wed/Thu, B is Sat/Sun/Tue/Thu. Floors and cleaners are split evenly; a new room joins the lighter pattern.

Closure-aware

Offices shut on Friday, so a Thursday sweep brings every every-other-day room forward. Saturday opens the week with the full round.

A work day, not a calendar day

The day rolls over at 3am, so a late shift still belongs to the day it started.

Hand-out rules

Only leaders get rooms, two early rooms each. An early room nobody can take stays visibly unassigned. Pinned rooms never move.

Fair rotation

Assistants are dealt to a new leader each Saturday; two teams are drawn for Friday, fewest past Fridays first. Seeded by date, so every device agrees.

Attendance capture

  1. Staff check in at the building's door system as they arrive.
  2. Through the day, the app collects each person's first check-in.
  3. It matches each check-in to the staff list.
  4. The roll call shows everyone as present, late or no scan.

Exception Reporting Framework

Each check compares what should have happened with what the books show and lists only the differences, each with a reason a person can act on. The check finds it; a person decides.

Ledger vs bills: do the books agree with the documents?

Receivables tie-out

Accounts Receivable must equal what the bills say customers owe. Because every ledger line carries its bill, a line attached to no bill is an exception by definition.

Duplicate postings

Its first run found payments an earlier version of the reconcile screen had posted a second time, against no bill. Each affected bank row is now flagged red, so it is reviewed before anything is removed.

Payout vs booking: did the money match the stay?

Next on the list Planned

Today each Airbnb payout is matched by hand on the Recon screen to the stay bill it pays, and the guest's account shows every stay, bill and payment together. The planned check pairs each booking with the payout that should follow it, and lists stays with no payout after the expected date, payouts that match no stay, and payouts that differ from the bill by more than the platform fee.

Why these

TypeScript and Next.js

One language and one deploy for screens and API, so a rule is written once, and a money field passed as text is caught before it reaches the ledger.

Postgres and plain SQL

Accounting needs transactions, foreign keys and constraints. A rule in the database holds for imports and scripts, not just screens.

Supabase for cleaning

Live sync between phones and TVs, plus a login, without running a server.

One file for cleaning

It changes daily on feedback from the floor. With no build step, a fix is a single push.

What I would do differently at scale

Replayable schema

Start from a canonical schema dump and have CI build a fresh database on every change; some base tables predate the migration history.

Connection pooling

At higher load, a connection pooler would sit in front of the database.

Tests on the money paths

Posting, reconciliation and check-out tested against a throwaway database before every deploy.

Row-level sync

The cleaning state is one JSON row, so the last device to save wins. Each room's status would become its own row or an event.

Modules and a build step

The 16,700-line file has outgrown itself: split it into modules, keep the no-server deploy.

One model for every building

Only one building is modelled unit by unit; at scale every building shares the same model. Staff matched on badge codes, not names.
